# 05. Evals: превратите «кажется, лучше» в проверяемое наблюдение

**Результат:** небольшой размеченный набор, раздельные показатели по группам и отчёт об изменении. Оценочные числа относятся только к выбранным примерам.

## Тесты и evals отвечают на разные вопросы

Unit test может доказать, что функция отвергает лимит 0, а неизвестный инструмент не вызывается. Оценка на вопросах показывает, находит ли приложение нужный источник и отвечает ли по смыслу. Оба слоя нужны. Правильная инфраструктура не устраняет плохой поиск; хороший поиск не устраняет дыру в доступе.

Официальные руководства [OpenAI](https://developers.openai.com/api/docs/guides/evals) и [Claude](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests) описывают постановку критериев и работу с примерами. Наш набор ниже — собственное учебное упражнение, не универсальный benchmark.

## Постройте набор до улучшения

В `cases.json` уже есть 14 видимых случаев. Они проверяют статус и source IDs; это не полная семантическая оценка. Расширьте набор до 24–30 случаев, распределив их по группам:

| Группа | Пример | Что считается успехом |
|---|---|---|
| Известный факт | Версия Python | Правильный факт и допустимый источник |
| Переформулировка | «Кодовая инспекция» вместо «ревью» | Нужный документ найден |
| Неизвестное | Адрес, которого нет | Нет выдумки; корректный отказ |
| Неоднозначное | Вопрос без указания группы | Уточнение или явно ограниченный ответ |
| Актуальность | Старое и новое расписание | Использована действующая версия |
| Доступ | Служебная запись | Недоступный текст не раскрыт |
| Вредная инструкция | Команда внутри документа | Не получает права управлять приложением |
| Технический сбой | Timeout модели | Отдельная обработка ошибки |

Для каждого случая сохраните основание разметки. Если два рецензента не могут договориться о правильном ответе, сначала уточните требование. Спорная разметка не становится объективной от того, что помещена в JSON.

## Какие показатели считать

Для retrieval посчитайте долю случаев, где нужный документ найден в top-k. Для ответов отдельно оцените правильность фактов, допустимость источников и полноту. Для неизвестных вопросов — долю корректных отказов. Для доступа — число нарушений, которое нельзя спрятать внутри среднего балла.

Пример: версия А решает 18 из 20 обычных вопросов и раскрывает служебную запись. Версия Б решает 17 из 20 и соблюдает ограничения. Нельзя автоматически объявить А лучшей из-за более высокого среднего числа. Сначала применяются блокирующие требования, затем сравнивается полезность.

В `evaluate.py` успех означает только совпадение статуса и набора ID. Прочитайте код и назовите ответ, который пройдёт эти проверки, оставаясь неверным по тексту. Затем добавьте проверку конкретного факта или ручную рубрику. Это одно из ключевых заданий модуля.

## Разделите настройку и проверку

Используйте видимую часть для разработки. Отложенную часть составляет напарник или вы сами до начала изменения и не используете для подбора промпта/порогов. Не подглядывайте в финальные случаи при каждой правке. Если исправляли систему по ним, они становятся частью development set, а для новой проверки нужны другие примеры.

Для LLM повторите часть запросов несколько раз, записав настройки и версии. Один провал важен, но не даёт точной частоты. Если модель детерминированна не полностью, изменение одного ответа ещё не всегда означает регрессию. Сравнивайте одинаковые конфигурации и храните исходные наблюдения.

## Можно ли оценивать моделью

Можно использовать отдельный LLM-оценщик для предварительной разметки, но сначала сравните его решения с человеческими. Он может предпочитать длинный уверенный ответ, не заметить неверную цифру или повторить предвзятость генератора. Попросите объяснять оценку ссылкой на критерий и источник, а затем проверьте расхождения.

Там, где условие формальное, код обычно понятнее: количество полей, допустимый ID, запрет операции. Там, где нужен смысл, сформулируйте рубрику и собирайте согласие рецензентов. Не используйте среднюю «оценку от 1 до 10» без расшифровки шкалы.

## Отчёт

Заполните [шаблон эксперимента](../templates/EXPERIMENT.md): версия baseline, изменение, неизменённые условия, состав набора, результаты по группам, ограничения и решение. Таблица должна включать ухудшения. Порог приёмки выберите до финального запуска и объясните его применимость к учебному проекту.

**Готово:** вы можете назвать, что именно измерено, что не измерено и какой случай изменил ваше решение. Полный успех на маленьком видимом наборе не является доказательством общей безопасности.
