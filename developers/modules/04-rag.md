# 04. Поиск, контекст и RAG: найдите причину ошибки

**Результат:** сравнение исходного поиска и одного улучшения на одинаковых вопросах. Сначала используйте локальный стенд; модель подключайте после проверки поиска.

## Что делает RAG

Retrieval-Augmented Generation — способ дать генератору выбранные сведения из внешнего корпуса. Он включает как минимум поиск и составление ответа. В лаборатории реализован только простой поиск и извлечение текста. Это baseline для будущей генерации, а не полноценная нейросетевая RAG-система.

Ошибки возникают на разных стадиях. Документа может не быть в базе; он может устареть; нужный фрагмент может не найтись; модель может проигнорировать найденный факт. Лечение этих ошибок различается. Если в корпусе нет адреса, увеличение числа токенов не создаст достоверный адрес.

## Разберите корпус

Откройте `documents.json`. У записи есть ID, заголовок, текст, теги и доверенные метаданные доступа/актуальности. В базе специально присутствуют архивная и служебная синтетические записи. Их наличие в учебном файле не означает, что пользователь приложения должен их получать.

Сейчас политика проста: выдаются только активные публичные записи. Фильтр применяется до поиска и возвращения текста. В реальном сервисе права должны вычисляться из подтверждённой личности и серверной политики; параметр `role=admin`, присланный клиентом, не создаёт полномочий.

## Почему простой поиск иногда полезнее сложного

Он дёшев, воспроизводим и легко объясним. Для небольшого корпуса с точными терминами его может хватить. В нашем примере score — доля значимых слов запроса, найденных в документе/тегах. Это не вероятность истины и не оценка уверенности LLM.

Проверьте две пары:

```text
ревью подготовка
кодовая инспекция
```

```text
встреча длительность
встреча адрес
```

Первая пара выявляет синонимы; вторая — похожую тему с отсутствующим фактом. Изменение порога может уменьшить ложные ответы, одновременно потеряв полезные. Нет числа, которое автоматически решает обе задачи для любого корпуса.

## Практика: одно улучшение

Выберите вариант и заранее опишите ожидаемый эффект:

- добавить нормализацию терминов и несколько синонимов;
- разделить длинные документы на смысловые фрагменты;
- добавить embeddings-поиск;
- сначала найти широкий список, затем переранжировать кандидатов.

Документация [Sentence Transformers](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html) разделяет retrieval и reranking. Для первого упражнения не обязательно устанавливать модель: начните с понятной небольшой правки. Если выбрали embeddings, запишите модель, размерность, способ построения индекса и стоимость/время. Не переиндексируйте приватные материалы ради тренировки.

Сохраните baseline, выполните изменение в ветке, запустите те же случаи. Затем попросите напарника составить пять новых переформулировок. Улучшение только на уже видимых фразах может быть подгонкой, а не общим улучшением поиска.

## Chunking и потеря смысла

Представьте документ: «Встреча в среду. Для группы Б — в пятницу». Если разделить его после первого предложения, вопрос про группу Б может получить среду. Фрагмент должен сохранять необходимые ограничения, а метаданные — связь с документом и версией. Больший chunk даёт больше контекста, но приносит лишнее. Меньший — экономит токены, но может отрезать условие.

Добавьте такой синтетический пример сами. Проверьте, что ответ различает группы. Не используйте одну и ту же версию текста для настройки и финальной проверки изменения.

## Источники и неизвестность

Возвращаемый ID должен существовать среди разрешённых кандидатов. Но это лишь техническая проверка: документ может быть нерелевантным. Для ответа на вопрос об адресе запись «место не указано» подтверждает только отсутствие адреса. По нашей спецификации приложение не должно выдавать её как найденный адрес.

Определите, что показывать человеку: отказ, просьбу уточнить или несколько кандидатов без утверждения ответа. Правило должно зависеть от задачи, а не от желания всегда заполнить поле `answer` уверенным текстом.

**Готово:** есть таблица «случай → нужный источник → baseline → новая версия», минимум одна новая ошибка разобрана по стадии. Укажите, что осталось нерешённым.

**Вопрос для защиты:** если нужный документ уже в top-3, но ответ неверный, почему переход на другую базу векторов может ничего не исправить?
