# 11. Итоговый проект: покажите доказательства, а не только демонстрацию

**Результат:** небольшой репозиторий с работающим проектом, проверками, отчётом и понятными ограничениями. Он должен запускаться у другого человека.

## Выберите вариант честно

**А. Инженерный стенд без модели.** Улучшите поиск, контракт, ограничения инструментов и оценку. Это завершённый промежуточный проект по retrieval и инфраструктуре. Не называйте его нейросетевым помощником, если LLM не использовалась.

**Б. Приложение с моделью.** Добавьте адаптер и фактические вызовы, сравните с вариантом А на одинаковых задачах. Результат включает ошибки, задержку и стоимость, а не только красивый текст.

**В. Расширение интеграциями.** После работающего Б подключите MCP; A2A добавляйте при обоснованной сервисной границе. Совместимость подтверждается отдельным запуском. Нельзя заменить основной результат диаграммой нескольких агентов.

## Новые условия

Создайте собственный синтетический корпус вымышленного клуба или сервиса:

- не менее 10 актуальных документов;
- две архивные записи, противоречащие текущим;
- две записи с ограниченным доступом;
- один документ с вложенной вредной инструкцией для негативной проверки;
- несколько вопросов, на которые в корпусе нет ответа.

Условия — учебный масштаб, не стандарт промышленного RAG. Если код умеет читать только один общий public-корпус, явно объясните это и не заявляйте поддержку многопользовательских прав.

Пусть напарник подготовит пять новых вопросов после завершения настройки. Если работаете один, заранее отложите набор и не подбирайте по нему параметры. Для демонстрации возьмите и удачный ответ, и содержательную ошибку.

## Что должно лежать в вашем проекте

README с задачей, вариантом проекта и запуском; короткая спецификация; исходники; синтетический корпус; тесты; eval-набор; отчёт сравнения; модель угроз; сведения о версиях; известные ограничения. При использовании внешних библиотек сохраните сведения об их лицензиях и версии зависимостей. Не копируйте чужие школьные задания и ответы.

Использование ИИ опишите конкретно: какие части он предложил, что вы проверили, где исправили. Не надо публиковать весь личный чат. Достаточно понятной записи в отчёте или PR.

## Критерии приёмки

| Проверка | Что предъявить |
|---|---|
| Повторяемость | Команды запуска у другого человека и фактический вывод |
| Известные факты | Ответы с источниками на размеченных случаях |
| Неизвестные факты | Нормальные отказы без выдумок |
| Актуальность | Архив не подменяет действующую запись |
| Доступ | Недоступные данные не попадают в ответ, модель и журналы |
| Ограничение действий | Неизвестные инструменты, лишние аргументы и превышение бюджета блокируются |
| Измерение | Отчёт по группам, включая ошибки и отложенные случаи |
| Модельный вариант | Реальная конфигурация, вызовы, ошибки и затраты отдельно от заглушки |
| Интеграции | Паспорт и фактический межоперационный тест, если заявлены |
| Понимание | Вы объясняете решение и вносите небольшое новое изменение |

Требования безопасности и доступа блокируют приёмку, если нарушены. Для полезности на обычных вопросах задайте порог в спецификации заранее. Нельзя задним числом объявить любой полученный процент достаточным.

## Защита

Проведите [взаимную проверку](../PEER_REVIEW.md). Рецензент выбирает один случай из отчёта, проверяет его руками и предлагает новое условие. Автор объясняет путь данных: вход → разрешённые документы → решение → вызов инструмента, если был → ответ → проверка.

Затем ответьте: где модель действительно нужна; что сломается при смене провайдера; какой риск остался; по какому измерению вы выбрали новую версию. Если ответа пока нет, запишите вопрос и следующий эксперимент.

## Что написать в портфолио

Хорошее описание: «Собрал учебного помощника на синтетическом корпусе. Сравнил два поиска на таком-то наборе, проверил такие-то ограничения. Live-интеграция выполнена с такой-то конфигурацией. Такие-то случаи пока не решены».

Не пишите «production-ready», «полностью безопасный» или «ускоряет всех в 10 раз» без соответствующего доказательства. Учебный проект ценен прозрачностью инженерных решений.
