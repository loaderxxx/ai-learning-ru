# 10. CI/CD, наблюдаемость и стоимость результата

**Результат:** воспроизводимые проверки, пример журнала, оценка затрат и план возврата к предыдущей версии. Публичный деплой для выполнения модуля не обязателен.

## От локального запуска к повторяемому

Начните с другого человека или чистой временной папки. Может ли он получить ту же версию, запустить команды из README и увидеть ожидаемый результат? Если для запуска требуется неизвестный файл с вашего рабочего стола, проект ещё не воспроизводим.

Зафиксируйте runtime, зависимости и данные. У нашего исходного стенда нет сторонних пакетов, поэтому первая проверка проста. После подключения SDK нужен lockfile или другой механизм фиксации выбранных версий. Версия модели и конфигурация retrieval тоже часть эксперимента, хотя они могут не лежать в Python dependency file.

## CI и CD

CI автоматически выполняет проверки изменений. CD относится к подготовке или доставке выпуска; конкретный уровень автоматизации зависит от проекта. Зелёный CI означает только, что настроенные проверки прошли. Если они не проверяют права или смысл ответа, эти свойства не появляются автоматически.

Есть [пример workflow](../templates/python-ci.yml) для собственной копии проекта. Он находится в папке шаблонов и **не запускает GitHub Actions автоматически**. Чтобы использовать его, перенесите в `.github/workflows/` своего учебного репозитория и проверьте настройки. Документация: [GitHub, Python testing](https://docs.github.com/en/actions/tutorials/build-and-test-code/python).

Перед использованием изучите referenced actions и закрепите одобренные версии. Для более строгой воспроизводимости используют проверенные commit SHA; учебный пример показывает читаемые version tags. Workflow не должен получать secrets для проверки внешнего pull request.

## Практика: две проверки с разным смыслом

В CI запускайте unit tests как обязательный gate. Отдельно формируйте eval-отчёт и определяйте, какие регрессии блокируют выпуск. Не считайте код завершения `evaluate.py` сигналом «качество достаточно»: скрипт специально формирует наблюдения, даже когда baseline ошибается.

Для своей улучшенной версии создайте явную политику: ни одного нарушения доступа; корректные известные сценарии не ухудшились; оставшиеся ошибки перечислены. Порог полезности согласуйте до финального запуска и не меняйте только для получения зелёного статуса.

## Наблюдаемость

[OpenTelemetry](https://opentelemetry.io/docs/concepts/observability-primer/) различает логи, метрики и трассировки. В учебном проекте сначала достаточно структурированного журнала:

```json
{
  "request_id": "demo-001",
  "stage": "retrieval",
  "duration_ms": 4,
  "candidate_count": 2,
  "status": "ok",
  "app_version": "practice-v1"
}
```

Числа здесь вымышлены для иллюстрации формата. При выполнении задания записывайте измеренные значения. Не выводите ключи и полный текст каждого запроса по умолчанию. Подумайте, кто читает лог, сколько он хранится и как его удалить.

Измерьте отдельно retrieval, модель, инструменты и общий запрос. Для нескольких запросов покажите все наблюдения или медиану с размером выборки. p95 на очень маленьком наборе нестабилен; не превращайте его в обещание сервиса.

## Стоимость

Используйте фактические актуальные цены своего провайдера:

```text
цена запроса = входные токены × цена входа / единицу тарифа
             + выходные токены × цена выхода / единицу тарифа
             + стоимость поиска/инструментов/повторных попыток
```

Проверьте единицу тарифа: например, цена может быть указана за миллион токенов. Учитывайте повторные попытки и неуспешные запросы. Стоимость принятого результата также включает время человека, если каждый ответ требует ручного исправления.

Для расчёта без API возьмите условные учебные цены, ясно подпишите их и сравните два сценария по числу вызовов. Это модель затрат, не действующий тариф. Реальная модель должна иметь бюджет и способ остановки при его исчерпании.

## Отказ и откат

Предложите, что произойдёт, если модель недоступна: показать извлечённый фрагмент с явным обозначением режима, предложить повтор позже или вернуть техническую ошибку. Не скрывайте переход к другому режиму от пользователя.

Опишите откат: к какой версии кода и корпуса возвращаетесь, что происходит с индексом, как проверяется совместимость схемы. Если есть записи в БД, откат кода не обязательно отменяет изменения данных. В нашем read-only стенде задача проще, но полезно назвать это ограничение.

**Готово:** новый человек воспроизводит запуск, проверки имеют ясный смысл, журнал помогает найти сбой, расходы не бесконтрольны, сценарий отката описан. Если CI или live API не запускались — это прямо указано.
