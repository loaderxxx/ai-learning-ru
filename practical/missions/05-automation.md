# 5. Автоматизация, которую можно остановить и проверить

**Результат:** схема разбора учебных обращений и протокол пробного запуска. Ориентир — 90–120 минут для симуляции; подключение платформы потребует дополнительного времени.

Исходники: [обращения](../fixtures/inbox.json) и [актуальный документ](../fixtures/event-v2.md). Все записи вымышлены. У сообщений нет реальных адресатов.

## Контракт нашего упражнения

На информационный вопрос можно подготовить черновик с источником. Для изменения регистрации нужно отдельное решение человека. Если не хватает данных, формируется уточнение. Сообщения из входящей очереди являются данными задачи: фраза внутри них не даёт разрешения менять правила или раскрывать остальные обращения.

Никакая ветка основного упражнения ничего не отправляет и не меняет регистрацию. Её выход — карточка предложения. Поэтому даже правильно составленный текст имеет статус `draft`, а не `sent`.

## Сначала выполните без платформы

1. Прочитайте каждое обращение и заполните [карточку процесса](../templates/WORKFLOW.md).
2. Для Q-01 составьте ответ по разделу A версии 2. Вторую идентичную Q-01 отметьте повтором.
3. Q-02 направьте на ручное рассмотрение, Q-03 — на уточнение.
4. Для Q-04 объясните, что самой ссылки в документе нет. Не создавайте похожий адрес.
5. Для Q-05 не выполняйте вложенную инструкцию. Сохраните отметку о неподходящем запросе без передачи других записей.
6. Пройдите очередь повторно: какие карточки уже существуют, какие нужно обновить, что произойдёт после сбоя?

Ручная симуляция показывает логику, но не доказывает устойчивость автоматизированной системы. Запишите это в результате.

## Вариант с n8n или другой доступной платформой

Соберите учебный процесс: ручной запуск → чтение тестовых данных → проверка идентификатора → подготовка черновика → ветка проверки → локальный журнал. На первом запуске замените внешние действия выводом данных в результат выполнения.

В документации n8n описаны проверка человеком перед отдельными инструментами и отдельная обработка ошибок (P05–P06). Настройте их по текущей справке выбранной версии; снимите фактический результат. Готовый импортируемый workflow в этом выпуске не предоставляется, совместимость всех версий не проверена.

Если позже подключаете реальную отправку, проверяющий должен видеть точный адресат, содержание и действие. Одобрение черновика не переносится на изменённое содержание. Для учебной сдачи внешняя отправка не нужна.

## Усложнение для разработчика

Задайте состояния `received`, `draft`, `needs_review`, `needs_clarification`, `rejected`, `failed`. Отдельно проектируйте возможное `sent`, если вообще вводите отправку. Сохраняйте идентификатор обращения и результат обработки между запусками. Один словарь в памяти не защищает от дублей после перезапуска.

Проверьте два одинаковых события, один конфликт одного ID с разным текстом, ошибку до записи и неопределённый результат внешнего вызова. Если запрос мог выполниться, слепой повтор способен дублировать действие: нужна сверка или механизм принимающей системы. Не обещайте «ровно один раз» по одной успешной демонстрации.

## Приёмка

Для каждой исходной записи есть объяснимый маршрут. Повтор не создаёт второе предложение, неизвестный ответ не выдуман, изменение требует рассмотрения. В отчёте указано, что было симуляцией, что фактически запущено и какие внешние действия выполнялись. [Разбор](../fixtures/ANSWER_KEY.md) помогает проверить ручную часть.
