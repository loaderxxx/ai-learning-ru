# 13. Наблюдаемость, стоимость и осмысленная оптимизация

[English](13-observability.en.md) · [Карта пути](../README.md)

**До начала:** работающий сервис или CLI и набор evals. **Результат:** по одному request ID можно восстановить технический путь, увидеть затраты и обосновать изменение.

## Какие вопросы должен отвечать журнал

Какая версия кода и prompt работала? Какая модель была выбрана фактически? Был ли fallback? Какие tools запрошены и какие реально исполнены? Где возникла ошибка? Сколько было попыток и какова задержка? Ответы должны находиться без сохранения всех частных документов в логах.

Logs описывают события, metrics — агрегированные показатели, traces — связи операций одного запроса. Для малого проекта начните с JSON-событий и отчёта, а не с обязательной покупки платформы наблюдаемости. Trace ID не заменяет права доступа к самим журналам.

## Материалы

1. [OpenTelemetry traces](https://opentelemetry.io/docs/concepts/signals/traces/) — spans, контекст и связь дочерних операций. Начните с одного запроса, одной модели и одного tool.
2. [LiteLLM routing](https://docs.litellm.ai/docs/routing) — сопоставьте фактические попытки с настройками маршрута, timeout и fallback.
3. [Ollama API introduction](https://docs.ollama.com/api/introduction) — дополнительный путь локального инференса. Локальный endpoint сам по себе не доказывает отсутствие сетевой передачи всеми остальными компонентами.

## Практика

1. Введите события `request_started`, `model_started`, `model_failed`, `tool_requested`, `tool_completed`, `request_finished`. Разделяйте запрос действия и его успешное выполнение.
2. Добавьте request/trace ID, версию компонента, безопасное имя маршрута, статус и длительность. Исключите ключи, токены авторизации и сырые приватные тексты.
3. Для 20 учебных запросов постройте отчёт: число успехов/отказов/сбоев, p50/p95 задержки, число попыток, выполненных tools и неизвестных usage. При таком маленьком наборе перцентили нестабильны — укажите размер выборки.
4. Рассчитайте стоимость успешной задачи: все учтённые расходы эксперимента, включая неудачные попытки, retrieval и судью, разделённые на число успешных задач. При нуле успехов показатель не определён, не записывайте ноль.
5. Стоимость токенов берите из действующего тарифа конкретной модели на дату запуска. Сохраните тариф и источник в своём отчёте; эта программа не фиксирует универсальную цену.
6. Сравните одну оптимизацию: меньший контекст, более дешёвый маршрут, кэш или сокращение числа шагов. На том же наборе проверьте качество, задержку и утечки через кэш.
7. Добавьте бюджет до запуска и контроль фактических расходов после. Предварительная оценка не гарантирует, что провайдер выставит точно такую сумму.
8. Воспроизведите один сбой по журналу и конфигурации. Не пытайтесь восстановить удалённые приватные данные из подробного debug-лога.

## Пример интерпретации

Если новый вариант отвечает быстрее, но чаще выдумывает цены, ускорение не доказывает улучшение. Если первая модель часто падает и всегда запускается вторая, «дешёвый первый шаг» может увеличивать итоговую стоимость. Для вывода нужны все попытки, не только последний успешный вызов.

Для локальной модели отдельно фиксируйте устройство, модель/квантизацию, память, время ответа и сетевой режим. Отсутствие оплаты за API не означает отсутствие затрат на оборудование и эксплуатацию. Покупать новый компьютер ради этой главы не требуется.

**Самостоятельно:** внедрите маскирование чувствительных полей и тест, который проваливается при попадании вымышленного ключа в сериализованный лог.

**Готово:** наблюдаемость отвечает на вопросы о пути, сбое и затратах; неизвестные данные не заменены нулями; оптимизация подтверждена сравнимым экспериментом.
