# 12. Превратите прототип в воспроизводимый сервис

[English](12-delivery.en.md) · [Карта пути](../README.md)

**До начала:** контракты, тесты и модель угроз. **Результат:** сервис запускается другим человеком в чистой среде; есть проверка изменений и понятный откат.

## Что меняется после ноутбука

Один удачный запуск из IDE не подтверждает работоспособность сервиса. Появляются конфигурация, установка зависимостей, входные запросы, параллельные пользователи, ошибки интерфейса и обновления. Не добавляйте Kubernetes ради учебного endpoint: начните с самого простого воспроизводимого запуска.

HTTP API принимает данные, но не должен доверять переданному `tenant_id` как доказательству личности. В демонстрации допускается явно помеченная учебная identity; перед реальным использованием нужна серверная аутентификация. Секреты модели остаются на сервере, не в JavaScript браузера.

Если добавляете streaming, отделите «текст поступает», «ответ завершён» и «действие выполнено». Показанный пользователю фрагмент не является завершённым результатом и не должен запускать tool. Для длинных операций полезны job ID и статус, но постановка в очередь тоже не равна завершению работы.

## Материалы

1. [FastAPI tutorial](https://fastapi.tiangolo.com/tutorial/) — request body, response model, dependencies, errors, testing. Это один удобный путь для Python, а не обязательный framework для всех.
2. [Docker getting started](https://docs.docker.com/get-started/) — image, container, build, volumes и конфигурация. Контейнеризация не является доказательством безопасности.
3. [GitHub Actions: Python build and test](https://docs.github.com/en/actions/tutorials/build-and-test-code/python) — тестирование изменений. Перед публикацией workflow проверьте используемые версии actions и права.

## Последовательность работы

1. Создайте `/health` без раскрытия конфигурации и `/requests` с явной схемой входа/выхода. Не возвращайте пользователю содержимое exception.
2. Внедряйте модельный адаптер через конфигурацию. По умолчанию учебный сервис запускается с mock и явно показывает этот режим.
3. Напишите README: требования к среде, установка, тесты, запуск, пример запроса, ожидаемый ответ, остановка и ограничения.
4. Зафиксируйте зависимости. Добавьте `.env.example` с пустыми безопасными значениями. Проверьте архив/репозиторий на секреты.
5. Добавьте тест HTTP-контракта: правильный запрос, плохой JSON, длинный вход, технический сбой, неверная identity. Сеть к провайдерам в стандартной тестовой команде запрещена.
6. Добавьте минимальный CI: установка, статическая проверка, unit/contract tests. Live-тесты требуют отдельного явного запуска, разрешённых данных и бюджета; не подключайте ключи к чужим pull requests.
7. При необходимости соберите локальный контейнер с непривилегированным процессом и минимальными правами. Привязывайте учебный сервер к loopback, не открывайте его всему интернету.
8. Передайте проект проверяющему или запустите в новой чистой папке. Запишите расхождения с инструкцией и исправьте её.
9. Опишите откат: известный commit, версия конфигурации, порядок остановки, восстановление данных и проверка после возврата. Учебный откат выполните локально.

## Приёмка

Проверяющий должен получить ожидаемый ответ, увидеть контролируемую ошибку, запустить тесты и понять, где включается настоящий API. Публикация URL не обязательна; публичное развёртывание может стоить денег и открывать данные, поэтому требует отдельного решения.

**Самостоятельно:** добавьте отмену запроса из интерфейса. Проверьте судьбу выполняющегося серверного действия; закрытая вкладка не доказывает, что backend остановился.

**Готово:** чистый запуск воспроизводим, mock явно обозначен, тесты не тратят деньги, конфигурация отделена от секретов, откат описан и проверен локально. Факт написания CI YAML не объявляйте успешным удалённым CI-run.
