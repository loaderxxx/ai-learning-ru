# 05. Tool calling: модель предлагает, программа исполняет

[English](05-tools.en.md) · [Карта пути](../README.md)

**До начала:** адаптер и понятные ошибки. **Результат:** ограниченный цикл вызова инструментов с проверкой аргументов, прав и результата.

## Проследите полный цикл

Приложение описывает доступные функции. Модель возвращает предложение: имя инструмента, аргументы и идентификатор вызова. Приложение проверяет предложение, выполняет разрешённую функцию и возвращает модели результат с соответствующим ID. После этого модель может сформировать финальный ответ или запросить следующий шаг. Максимальное число шагов задаёт программа.

Это отличается от функции `summarize(text)`, которая сама вызывает AI и возвращает строку. В первом случае модель выбирает действие из предложенного набора; во втором выбор шага уже сделал обычный код. Для простой задачи агентный цикл может быть вовсе не нужен.

Схема инструмента сообщает допустимый формат, но не выдаёт права. Даже валидный `record_id` может принадлежать другому пользователю. Tenant и разрешения берутся из доверенного контекста приложения, не из аргумента, предложенного моделью.

## Читать

1. [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling) — tool definition, запрос вызова, выполнение на стороне приложения, возврат результата.
2. [Claude tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) — сопоставьте роли запросов и результатов; не переносите JSON одного SDK в другой без адаптера.
3. [Gemini function calling](https://ai.google.dev/gemini-api/docs/function-calling) — альтернативное представление той же границы. Для практики достаточно одного провайдера.

## Реализуйте безопасный минимум

1. Разрешите только `calculate_total` и `lookup_record`. Не добавляйте произвольное выполнение кода, shell, SQL или URL по строке модели.
2. Для каждой функции опишите имя, назначение, схему входа и выхода. Дополнительные поля отвергайте; числа проверяйте по типу и диапазону.
3. Добавьте диспетчер с явным allowlist. Не используйте `eval`, динамический импорт или поиск произвольной функции по имени из ответа.
4. Перед `lookup_record` проверяйте владельца записи по доверенному tenant. Отказ не должен раскрывать само содержимое чужой записи.
5. Возвращайте только минимальный необходимый результат. Содержимое tool-output считайте данными, а не новым разрешением менять систему.
6. Ограничьте число модельных вызовов и tool-шагов. Повтор одинакового call ID с другими аргументами должен быть обнаружен.
7. Запишите безопасный журнал: request ID, модель, имя tool, статус. Ключи, полный prompt и приватные документы в него не попадают.
8. После офлайн-тестов реализуйте провайдерный round trip: модель → tool request → приложение → tool result → финальный ответ. Без такого запуска нельзя объявлять живой tool calling проверенным.

## Контрольные случаи

Правильный расчёт: 250 × 4 → 1000. Неверный тип: `quantity=true` → отказ. Неизвестная функция `delete_all` → отказ до выполнения. Правильный ID чужого tenant → отказ. Бесконечные предложения lookup → остановка по лимиту. Вредная фраза в содержимом найденной записи → не расширяет allowlist.

Для первого стенда инструменты read-only или чистые вычисления. Запись в реальную систему потребует отдельной аутентификации, проверки актуальности согласования, идемпотентности и разрешения владельца. Слово «approved» внутри модельного ответа не является согласием человека.

## Докажите навык

Покажите последовательность сообщений с привязкой к call ID и отдельно тест, доказывающий, что запрещённая функция не исполнилась. Скриншот красивого финального ответа этого не доказывает.

**Самостоятельно:** добавьте `get_opening_hours` с двумя допустимыми значениями дня и отказом на остальные. Затем пусть модель запросит неподдержанный день. Объясните различие ошибки аргументов и отсутствия сведений в базе.

**Готово:** ни схема, ни текст модели не обходят права; финальный ответ отделён от tool request; цикл ограничен; есть негативные тесты.
