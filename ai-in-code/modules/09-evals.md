# 09. Evals: как доказать, что система стала лучше

[English](09-evals.en.md) · [Карта пути](../README.md)

**До начала:** есть baseline и несколько сценариев. **Результат:** воспроизводимый набор оценки, отчёт по ошибкам и обоснование одной правки.

## Не смешивайте разные проверки

Unit test проверяет конкретную функцию. Контрактный тест — совместимость компонентов. Интеграционный — реальное взаимодействие. Eval проверяет поведение AI-системы на задачах с критериями качества. Ни один из этих слоёв не заменяет остальные.

Начните с вопроса: какое решение должен поддержать эксперимент? Например, «нужен ли новый retrieval» или «ухудшит ли более дешёвая модель правильность расчётов». Не запускайте бессистемно сотни запросов ради красивого процента.

В этом курсе численность случаев и пороги — учебные условия, не отраслевые стандарты и не доказательство промышленной надёжности. Маленький корпус обнаруживает известные ошибки, но не измеряет редкие риски с высокой точностью.

## Создайте небольшой оценочный набор

1. Возьмите 20 синтетических случаев: восемь обычных, четыре неизвестных/неоднозначных, четыре запрета доступа или prompt injection, четыре ошибки формата/транспорта. Это стартовая учебная композиция.
2. Для каждого укажите ID, вход, разрешённые источники, ожидаемый статус, обязательные факты и запрещённые действия. Не требуйте единственной точной формулировки свободного текста.
3. Разделите набор на 12 случаев разработки и 8 отложенных случаев. Близкие перефразирования одной истории держите в одной части, чтобы не получить утечку через почти одинаковые примеры.
4. На части разработки улучшайте код и prompts. Отложенную часть используйте после выбора варианта; многократная подгонка превращает её в новый dev-набор.
5. Сначала запустите baseline, затем один изменённый вариант. Сохраняйте модель, версии prompt/корпуса/кода, параметры, seed где поддерживается, время и стоимость/usage.
6. Проверяйте отдельно: правильность статуса, подтверждённость фактов, доступ, отсутствие запрещённых действий, завершённость и задержку. Не скрывайте утечку данных за высоким средним баллом полезности.
7. Для недетерминированных случаев выполните несколько повторов по одинаковому протоколу и покажите разброс, не только лучший ответ.
8. Классифицируйте ошибки: retrieval, генерация, контракт, инструмент, права, транспорт. Исправляйте причину, а не просто удлиняйте prompt.

## Человек и модель-судья

Сначала разберите несколько ответов вручную по рубрике. Модель-судья может помогать масштабировать проверку, но не является истинной разметкой по определению. Проверьте её на согласованных человеком примерах, включая неверные, но убедительные ответы. Учитывайте стоимость судьи и его возможную зависимость от длины/стиля текста.

Пример: ответ с правильным `source_id` и неправильной ценой должен провалить содержательную проверку. Ответ `not_found` на вопрос без источника должен пройти, даже если он выглядит менее полезным.

## Что предъявить

Отчёт: вопрос эксперимента → baseline → изменение → полный набор результатов → ошибки → ограничения → решение оставить/откатить. Укажите знаменатель: «7 из 8 отложенных случаев», а не только «87,5% качества».

**Самостоятельно:** добавьте новый тип обращения, которого не было при настройке. Объясните, почему успешность на старом наборе не подтверждает качество в новой области.

**Готово:** другой человек может повторить сравнение; результаты не подменены отбором лучших ответов; критические нарушения видны отдельно. Live-оценка и офлайн-оценка mock помечены раздельно.
