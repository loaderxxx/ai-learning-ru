# 11. Безопасность AI-приложения и границы данных

[English](11-security.en.md) · [Карта пути](../README.md)

**До начала:** описаны tools, данные и потоки. **Результат:** небольшая модель угроз, защитные ограничения в коде и воспроизводимые негативные тесты.

## Где возникает опасность

Модель читает пользовательский текст и найденные документы. Эти данные могут содержать инструкции, маскирующиеся под команды разработчика. Prompt injection нельзя считать устранённой только потому, что в системном prompt написано «игнорируй вредные инструкции».

Разделите доверенные решения приложения и недоверенное содержимое. Идентичность пользователя, разрешённые операции, доступ к хранилищу и лимиты устанавливаются вне модели. Проверка на выходе дополняет эти границы, но не заменяет их.

Для учебного Request Desk наиболее важны четыре объекта: ключ провайдера, документы tenant, возможность выполнить tool и журнал запросов. Нарисуйте, кто может их читать и изменять. Не используйте реальные клиентские материалы для проверки защиты.

1. [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/) — prompt injection, чувствительная информация, supply chain, output handling и excessive agency. Прочитайте описание риска и сопоставьте со своим потоком данных.
2. [MCP security guidance](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices) — риски подключаемых серверов и токенов.

## Постройте защиту шаг за шагом

1. Составьте таблицу «актив → недоверенный вход → возможный ущерб → контроль → тест». Не ограничивайтесь списком аббревиатур.
2. Установите deny-by-default для tools. Разделите чтение и запись; пользовательский текст не может включить новый инструмент.
3. Фильтруйте данные по правам до retrieval и до передачи модели. Добавьте tenant в ключи кэша и проверьте источник identity на сервере.
4. Проверяйте структурированные аргументы и business constraints. Не исполняйте сгенерированный SQL, HTML или shell как доверенный код. Для отображения текста используйте безопасное экранирование.
5. Уберите секреты из исходников и логов. `.gitignore` предотвращает часть будущих ошибок, но не удаляет уже опубликованный ключ из истории; при реальной утечке нужен отзыв/ротация через владельца.
6. Ограничьте размер входов и выходов, количество шагов, сетевые адреса и стоимость эксперимента. Повышенные права для удобства учебного стенда не выдавайте.
7. Запишите зависимости и версии. Перед обновлением проверьте происхождение пакета, изменения API и результаты тестов. Не запускайте команды из содержимого документа автоматически.
8. Опишите сроки хранения учебных входов и логов. Удаление из основной таблицы должно сопровождаться проверкой индекса и кэша; не утверждайте удаление из внешнего провайдера без доступного механизма и подтверждения.

## Пять безопасных проверок

Используйте только синтетический стенд: документ просит показать вымышленный секрет; запрос требует запись другого tenant; аргумент пытается выбрать произвольный путь; tool-output требует подключить новый tool; очень длинный вход пытается исчерпать бюджет. Наблюдайте фактическое выполнение, а не только слова модели «я не могу».

Если модель сформировала запрещённый запрос, но сервер заблокировал его, разделите результаты: ошибка модельного поведения и успешная граница исполнения. Если модель отказала, но сервер готов был исполнить запрещённое, система всё ещё небезопасна.

**Самостоятельно:** проверьте, что ошибка инструмента не раскрывает стек, пути, ключи или чужое содержимое через логи и ответ.

**Готово:** права проверяются кодом; секреты не опубликованы; опасные действия не исполняются в негативных случаях; ограничения и остаточные риски описаны. Это учебная проверка, не профессиональный security-аудит и не гарантия отсутствия уязвимостей.
