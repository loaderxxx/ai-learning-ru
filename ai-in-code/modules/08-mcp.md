# 08. MCP: подключите инструмент, не перепутайте протокол с доверием

[English](08-mcp.en.md) · [Карта пути](../README.md)

**До начала:** умеете выполнять и ограничивать обычные tools. **Результат:** небольшой read-only MCP-сервер и подтверждённое взаимодействие с клиентом либо честно отмеченный проект интеграции без запуска.

## Зачем нужен отдельный протокол

MCP стандартизирует обмен между AI-приложением и серверами, предоставляющими возможности. Host управляет пользовательским приложением, client поддерживает соединение с сервером, server предоставляет инструменты и другие ресурсы. Модель не обязана напрямую говорить по MCP: host связывает протокол с модельным SDK.

Tool — вызываемая операция, resource — доступный контекст/данные, prompt — предоставляемый шаблон взаимодействия. Это не три вида разрешений. Объявленная возможность не означает, что приложение обязано её разрешить пользователю или модели.

Для локального учебного сервера используйте stdio: отдельный процесс, запросы/ответы по стандартным потокам. Диагностический вывод отправляйте в stderr, чтобы не испортить протокольный stdout. Для сетевого сервера отдельно изучайте Streamable HTTP, аутентификацию и авторизацию. «Работает на localhost» не заменяет оценку рисков подключаемого процесса.

## Материалы

1. [Официальная архитектура MCP](https://modelcontextprotocol.io/docs/learn/architecture) — host/client/server, lifecycle, capabilities и примитивы. Запишите версию спецификации, которую фактически используете.
2. [MCP security best practices](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices) — границы доверия, token handling, ограничения клиента/сервера.
3. [Существующий модуль MCP](../../developers/modules/07-mcp.md) — дополнительный русский паспорт интеграции. Документация выбранного официального SDK имеет приоритет для конкретных API.

## Лабораторная работа

1. Выберите SDK по ссылке из официальной документации MCP и зафиксируйте версию. Не устанавливайте случайный одноимённый пакет.
2. Создайте сервер с единственным `lookup_public_note(note_id)`, который читает три заранее заданные синтетические записи. Никакой записи файлов, shell или произвольного пути.
3. Вход проверяйте в сервере, даже если клиент уже использует схему. Возвращайте понятный результат или структурированную ошибку.
4. Подключите совместимый клиент. Подтвердите инициализацию, получение списка tools и один вызов. Сохраните очищенный transcript протокола и версии обеих сторон.
5. Вызовите неизвестный ID, неверный тип и лишний аргумент. Проверьте отказ, не раскрывающий окружение процесса.
6. Остановите сервер во время запроса. Клиент должен завершить ожидание по timeout и показать техническую ошибку.
7. Подключите этот инструмент к вашему модельному циклу как отдельный следующий опыт. Работа MCP-клиента без модели подтверждает протокол, но не весь AI-workflow.
8. Запишите ограничения: локальный или сетевой транспорт, доступные операции, права процесса, аутентификация, выполненные тесты и что пока не проверялось.

## Границы, которые нельзя пропустить

Сервер с убедительным описанием всё равно может быть недоверенным. Права процесса должны быть минимальны. Токен одного сервиса нельзя бездумно пересылать другому. Для HTTP изучите audience, происхождение запросов, проверку адресов и требования авторизации своей версии протокола; не переносите настройки stdio как готовую сетевую защиту.

Демонстрация `tools/list` не доказывает, что инструмент исполнился. В ответе покажите фактический результат `tools/call`, версию сервера и негативную проверку. Не называйте обычную Python-функцию MCP-интеграцией только потому, что она называется tool.

**Самостоятельно:** измените формат ответа сервера и обнаружьте несовместимость контрактным тестом, прежде чем подключать новую версию к модели.

**Готово:** есть воспроизводимый handshake и вызов, отрицательные случаи, тайм-аут и паспорт интеграции. При отсутствии запуска статус — `DESIGN ONLY`, а не «MCP поддерживается».
