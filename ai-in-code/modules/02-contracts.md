# 02. От задачи к контрактам: где действительно нужен AI

[English](02-contracts.en.md) · [Карта пути](../README.md)

**До начала:** этапы 00–01. **Результат:** одностраничная спецификация, схема потока данных и baseline без модели.

## Три разных направления вызова

`classify_request(text)` может быть обычной функцией вашего приложения, которая внутри обращается к LLM. Это **код вызывает модель**. В tool calling модель возвращает предложение `lookup_record(id)` — это **модель запрашивает действие**, а выполняет его программа. Orchestration связывает оба направления в процесс. MCP описывает взаимодействие с инструментами, но не заменяет бизнес-логику. Не смешивайте эти уровни в одном слове «агент».

В нашем учебном проекте **Request Desk** помощник обрабатывает синтетические обращения клуба. Он находит разрешённую справку, считает сумму обычным кодом и готовит черновик. Он не отправляет сообщения, не платит и не меняет реальные аккаунты. Название и все данные — учебные.

Разложите запрос «Объясни стоимость четырёх занятий и подготовь ответ» на действия. Поиск цены — обращение к данным. Умножение — код. Формулировка объяснения может использовать модель. Отправка — отдельное действие с отдельным разрешением; в учебном проекте она отсутствует.

## Напишите спецификацию по шагам

1. Сформулируйте пользователя и одну задачу: «получить подтверждённый ответ по учебным материалам». Не пишите «универсальный ассистент для всего».
2. Задайте допустимые входы, длину, язык, `tenant_id` и источник идентичности. Tenant устанавливает приложение после аутентификации, а не модель из текста запроса.
3. Опишите выход как явные состояния: `answered`, `not_found`, `needs_approval`, `invalid_input`, `technical_error`. Поля результата должны зависеть от состояния предсказуемо.
4. Перечислите разрешённые tools и запреты. Укажите, что фраза внутри документа не выдаёт прав.
5. Подготовьте 10 вымышленных обращений: прямой вопрос, перефразирование, неизвестное, конфликт документов, запрос чужих данных, расчёт, плохой вход, timeout, повтор действия, вредная инструкция в источнике.
6. Решите их вручную и запишите ожидаемое поведение **до** настройки модели.
7. Сделайте baseline: словарный поиск и шаблонный ответ. Измеряйте пользу AI относительно этой версии, а не относительно отсутствия программы.

## Пример контракта

```json
{"request_id":"demo-01","status":"answered","answer":"Four sessions cost 1000 cents.","source_ids":["price-v1"]}
```

Это иллюстрация формата, не доказанный ответ. Проверяющий должен убедиться, что `price-v1` существует, разрешён этому пользователю и действительно содержит цену `250` за занятие. JSON с тем же ID и ценой `900` всё ещё структурно корректен, но содержательно неверен.

Для `not_found` не выдумывайте цену. Для конфликта двух действующих документов не выбирайте удобный без правила приоритета: покажите конфликт или запросите уточнение. Порядок авторитетности и актуальности данных запишите заранее.

## Переход дальше

Покажите три случая, где обычный код достаточен, и один, где хотите проверить полезность LLM. Объясните разницу между prompt, контрактом, правом доступа и тестом.

**Самостоятельно:** измените условие — теперь часть документов доступна только другому клубу. Отметьте все места фильтрации: retrieval, кэш, модельный контекст, ответ и логи.

**Готово:** другой разработчик понимает, что строить, какие действия запрещены и по каким примерам проверять результат. Используйте [WORKBOOK](../WORKBOOK.md) для записи решения.
