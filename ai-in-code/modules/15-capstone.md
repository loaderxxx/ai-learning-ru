# 15. Итоговый проект Request Desk и технический разговор

[English](15-capstone.en.md) · [Карта пути](../README.md)

**Результат:** небольшой AI-сервис, который другой инженер может запустить, проверить и обсудить. Это учебная работа на синтетических данных, а не бесплатное выполнение клиентской задачи.

## Задание

Request Desk принимает обращение в вымышленный клуб. Он определяет тип задачи, получает разрешённую справку, выполняет точный расчёт обычным кодом и готовит ответ с источниками. При недостатке сведений не выдумывает; при запросе чужих данных отказывает. В демонстрации он не отправляет письма, не оплачивает счета и не меняет реальные аккаунты.

Основной язык выбираете сами. Для Python доступен [стартовый mock-стенд](../lab/README.md), но он **не является готовым итоговым проектом**. Retrieval, настоящий API, MCP, база, HTTP-сервис и persisted approvals — отдельные реализации ученика по предыдущим этапам.

## Собирайте по контрольным точкам

### A. Контракт и baseline

Опишите пользователя, входы, выходы, ограничения и права. Подготовьте синтетический корпус и разметку. Покажите работающую версию без модели. Статусы: `answered`, `not_found`, `needs_approval`, `invalid_input`, `technical_error`; доступ к чужому содержимому не раскрывает его.

### B. Модель и инструменты

Добавьте общий интерфейс к двум маршрутам, один реальный provider при доступе, проверяемую структуру ответа и read-only tools. Покажите полный round trip с call ID. Две заглушки не называйте двумя подключёнными моделями; второй mock допустим, но остаётся явным пробелом.

### C. Данные и контроль

Добавьте retrieval с ACL до модельного контекста, цитаты, правила актуальности и отказ при неизвестном. Продемонстрируйте ограничение шагов, один безопасный fallback, тайм-аут и отрицательные проверки. MCP реализуйте как расширение с отдельным паспортом; его отсутствие не маскируйте названием функции.

### D. Проверка и передача

Запустите 20 размеченных случаев по схеме этапа 09, отделив 12 dev и 8 held-out. Подготовьте отчёт об ошибках, а не только процент успеха. Добавьте запуск из чистой среды, безопасные логи, информацию о затратах и инструкцию отката. Другой человек должен суметь повторить хотя бы локальный путь.

## Сценарии приёмки

| Сценарий | Ожидаемое наблюдаемое поведение |
|---|---|
| Четыре занятия по 250 центов | Tool возвращает 1000; ответ ссылается на актуальную цену |
| В документах нет ответа | `not_found`, без вымышленной ссылки |
| Два действующих документа противоречат | Конфликт обозначен либо применено заранее записанное правило |
| Чужой tenant/источник | Данные не попадают в модель, ответ или кэш другого пользователя |
| `quantity=true`, неизвестный tool | Отказ до исполнения |
| Временный сбой модели | Ограниченный допустимый fallback или технический статус |
| Запрос без права на внешний provider | Никакой утечки через запасной маршрут |
| Бесконечный цикл предложений | Остановка по лимиту с понятной причиной |
| Инструкция в документе расширить права | Allowlist и доверенная identity не меняются |
| Повтор локальной записи в дополнительном задании | Один эффект с проверкой ключа/аргументов; после restart тоже |

Эти случаи — проверяемый минимум учебного проекта, не полный security-аудит. Схема/ссылка подтверждает формат, но смысл ответа нужно проверять отдельно.

## Что принести на разговор

Ссылка на собственный код или приватная демонстрация; README запуска; краткая архитектура; версии SDK/модели/корпуса; таблица тестов и evals; пример удачного и неудачного запроса; описание того, где использовали AI при разработке; список известных ограничений. Чужой закрытый код и клиентские документы не публикуйте.

В [WORKBOOK](../WORKBOOK.md) есть шаблоны. У каждого навыка укажите: прочитано, воспроизведено, применено, объяснено на новом условии. Рекрутеру важнее честная граница, чем десятки названий библиотек.

## Защита понимания

Объясните без подсказки: почему здесь нужна модель; что происходит при её отказе; кто исполняет tool; как установить права; что не покрывают тесты; как заменить провайдера; почему валидный JSON бывает неверным; как повторить запись безопасно; какую часть вы бы оставили обычным кодом.

Проверяющий меняет одно условие: другой формат записи, неподдержанный tool или новая неоднозначность. Ваша задача — локализовать изменение и добавить проверку, а не переписать проект вслепую.

**Готово для обсуждения:** воспроизводимый проект и объяснимые ограничения. Это не обещание трудоустройства, диплом или автоматический доступ к реальной инфраструктуре. Опытный кандидат может показать эквивалентный существующий проект вместо прохождения всех глав.
