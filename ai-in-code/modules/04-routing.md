# 04. Несколько моделей: адаптеры, routing и fallback

[English](04-routing.en.md) · [Карта пути](../README.md)

**До начала:** этап 03 или его контрактная часть. **Результат:** бизнес-логика не привязана к одному SDK; правила выбора и замены модели проверяются независимо от сети.

## Что именно вы строите

Адаптер переводит запрос приложения в формат провайдера. Router выбирает допустимый адаптер. Fallback определяет поведение после определённого сбоя. Это три разные обязанности. Две модели одного провайдера дают возможность сравнения, но не доказывают независимость от провайдера.

Одинаковый интерфейс не делает модели полностью взаимозаменяемыми. Могут отличаться поддержка tools, схемы, размер контекста, streaming, форматы отказа и правила обработки данных. Внутренний контракт должен либо использовать общие возможности, либо явно проверять требуемые capabilities. Не удаляйте ограничение безопасности ради успешного fallback.

Начните с простого правила: расчёт выполняет код; краткую классификацию — доступная модель A; сложную формулировку — модель B. Это учебная гипотеза, не утверждение, что конкретная модель дешевле или лучше. Проверьте правило на одинаковых задачах.

## Материалы

1. [LiteLLM introduction](https://docs.litellm.ai/docs/) — различие Python SDK и отдельного proxy. Для первого опыта достаточно SDK или собственных двух адаптеров.
2. [LiteLLM routing](https://docs.litellm.ai/docs/routing) — model groups, retries, fallbacks, timeouts. Читайте параметры для установленной версии, а не переносите конфигурацию из старого примера без проверки.
3. Вернитесь к [контракту API](03-model-api.md): структура, отказ, usage и ошибка должны иметь одинаковый смысл для вызывающего кода.

## Практика

1. Определите внутренний интерфейс `generate(request) -> result`. В запросе передавайте требования к формату и разрешённому маршруту; в результате сохраняйте фактически использованный provider/model.
2. Создайте два mock-адаптера. Первый может выдавать временную ошибку; второй — правильный ответ. Проверьте маршрутизацию без ключей.
3. В конфигурации задайте capabilities и допустимые категории данных каждого маршрута. Пользовательский текст не должен менять эти разрешения.
4. Реализуйте один ограниченный fallback только для заранее определённых временных сбоев. Неверный ключ, запрещённые данные и нарушение контракта не должны автоматически отправлять запрос третьей стороне.
5. Выберите одного живого провайдера и проведите отдельную интеграционную проверку. Второго подключайте только при доступе и разрешённых условиях передачи данных.
6. Сравните 10 одинаковых синтетических задач: результат, задержка, число попыток, usage, ошибки. Не выбирайте модель только по самому красивому ответу.
7. Замените один адаптер, не меняя доменную функцию. Покажите diff и повторите контрактные тесты.

## Разберите отказ

Модель A получила запрос, но соединение оборвалось. Для чистой генерации повтор может быть допустим в пределах бюджета, хотя первая попытка уже могла стоить денег. Для tool, меняющего состояние, нельзя считать отсутствие ответа доказательством отсутствия действия. Возврат к записи после такого сбоя изучается отдельно на этапе 10.

Fallback также не должен обходить явный отказ по политике или правам. Цель — устойчивость разрешённого процесса, не поиск провайдера, который выполнит запрещённое действие.

## Артефакт и проверка

Сохраните таблицу маршрутов, два тестовых сценария отказа и паспорт каждого реально проверенного соединения. Для заглушки пишите `MOCK`, для неисполненного адаптера — `NOT RUN`; для двух моделей одного API — именно «две модели одного провайдера».

**Самостоятельно:** добавьте условие «эти данные нельзя отправлять внешнему провайдеру». При недоступности допустимого маршрута система должна остановиться, а не выбрать запрещённый запасной.

**Готово:** выбор модели объясним, fallback ограничен, реальные вызовы отделены от mock, замена SDK не меняет бизнес-правила.
