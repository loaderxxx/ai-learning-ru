# 06. Orchestration: от последовательности функций к графу состояний

[English](06-workflows.en.md) · [Карта пути](../README.md)

**До начала:** выполнен безопасный tool loop. **Результат:** процесс с явными состояниями, условиями перехода и остановки; затем сопоставимая реализация на выбранном framework.

## Начните без framework

Для Request Desk достаточно цепочки: проверить вход → классифицировать → получить разрешённые сведения/посчитать → проверить результат → подготовить ответ. Ветка `not_found` заканчивается отказом от догадки. Ветка технической ошибки заканчивается объяснимым статусом. Запись или отправка не добавляются автоматически.

Workflow заранее определяет допустимые переходы. Агент может выбирать следующий шаг динамически, но всё равно внутри ограничений программы. Сложность оправдана только дополнительной способностью, которую нельзя удобнее получить простыми функциями.

Состояние — данные выполнения: `request_id`, доверенная идентичность, статус, найденные source IDs, результаты tools, счётчики и ошибки. Не храните секреты или неограниченный чат в общей структуре. Не путайте состояние одного запуска, долгосрочную память пользователя и базу документов.

## Материалы

1. [LangGraph overview](https://docs.langchain.com/oss/python/langgraph/overview): state, nodes, edges; LangGraph можно использовать без LangChain.
2. [Workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents): chaining, routing и динамическое управление. Выберите один паттерн для одной задачи.
3. [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence): checkpoints, threads, восстановление. Сохранённое состояние не делает внешние действия автоматически безопасными при повторе.

## Соберите две версии

1. Нарисуйте таблицу: текущее состояние, условие, действие, следующее состояние. У каждого пути должен быть терминальный исход.
2. Реализуйте таблицу обычным Python. Для классификации используйте mock или адаптер этапа 03. Сохраните эту версию как baseline.
3. Введите лимит шагов, общий deadline и явный статус `needs_approval` для пока неисполняемого намерения записи.
4. Запретите переход напрямую от недоверенного текста к выполнению write-tool. Approval привязывается к конкретному действию и аргументам, а не ко всей беседе.
5. Установите выбранный framework в отдельном окружении, запишите версию. Перенесите тот же процесс в LangGraph или эквивалентный инструмент вашего стека.
6. Прогоните одни и те же случаи на обеих реализациях. Выходные статусы и ограничения должны совпадать, даже если внутреннее устройство разное.
7. Добавьте checkpoint перед разрешённой точкой остановки. Завершите процесс и восстановите его. Проверьте, какие шаги повторились, а какие не должны повторяться.
8. Запишите, что дал framework: визуально ясные переходы, управляемая пауза, сохранение состояния или другое измеримое удобство. Если он лишь усложнил простой сценарий, это допустимый вывод.

## Пример разбора

Для обращения без источника маршрут `retrieve → not_found → finish` правильнее, чем `retrieve → model guesses → answered`. Для превышенного бюджета маршрут `budget_exhausted → finish` не должен возвращаться в `retry`.

При восстановлении после сбоя нельзя предполагать, что отправка письма не произошла только потому, что следующий checkpoint не сохранился. Это граница между памятью workflow и внешним побочным эффектом; отдельное решение нужно на этапе 10.

## Проверка понимания

Объясните, что определяет код, что выбирает модель, где сохраняется state, как ограничен цикл и почему сохранение history не является системой авторизации. Покажите путь с ошибкой и путь с паузой, а не только успех.

**Самостоятельно:** добавьте ручную проверку черновика. После изменения текста черновика старое согласование должно перестать действовать. Реальная отправка по-прежнему отсутствует.

**Готово:** граф имеет явные остановки; baseline сохранён; ошибки и восстановление проверены; framework не расширяет права.
