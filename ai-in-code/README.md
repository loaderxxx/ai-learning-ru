# AI внутри программы: модели, tools и orchestration

Это новый учебный пункт для тех, кто уже умеет программировать и хочет, чтобы **обычный алгоритм сам обращался к AI-моделям, выбирал нужную модель и давал модели доступ к функциям программы**.

Пока это стартовая страница-задание. Полный курс и лаборатории будут добавляться позже.

## Как это называется

Здесь важно различать четыре вещи:

1. **AI / LLM API и SDK** — программа сама вызывает модель как обычный сервис.
2. **Multi-provider LLM router / gateway** — один интерфейс программы работает с несколькими провайдерами и моделями.
3. **Tool / function calling** — модель может запросить вызов разрешённой функции программы или API.
4. **LLM / agent orchestration** — код связывает несколько шагов, моделей и инструментов в один управляемый процесс.

Это не отдельный язык программирования. Это слой библиотек и SDK поверх Python, JavaScript/TypeScript, C#, Java и других языков.

## Что предлагаю изучить сначала

### 1. Вызов модели из обычной программы

Научитесь:
- отправлять запрос модели из кода;
- получать текстовый и структурированный ответ;
- обрабатывать timeout, ошибку API и неверный формат;
- не хранить API-ключи в коде и Git.

Если это ещё не проходили, начните с нашего модуля: [API моделей и структурированный ответ](../developers/modules/03-model-api.md).

### 2. LiteLLM — один интерфейс к разным моделям

Изучите **LiteLLM**: библиотеку и gateway, которые позволяют обращаться к множеству LLM-провайдеров через единый интерфейс, а также настраивать routing, retry и fallback.

Цель: понять, как написать бизнес-логику так, чтобы она не была намертво привязана к одной модели или одному провайдеру.

Официальная документация: https://docs.litellm.ai/docs/

### 3. Tool / function calling

Научитесь давать модели ограниченный набор функций, например:

- получить данные;
- выполнить расчёт;
- вызвать внутренний API;
- записать проверенный результат;
- передать задачу другому компоненту.

Важно: модель **не исполняет вашу функцию сама**. Она формирует запрос на вызов, а программа проверяет аргументы, права и только потом выполняет действие.

Наш базовый модуль: [Вызовы инструментов и агенты](../developers/modules/06-tools-agents.md).

### 4. LangChain + LangGraph — orchestration

Изучите базовые идеи **LangChain** и **LangGraph**:

- модели и адаптеры;
- tools;
- последовательности шагов;
- состояние;
- routing;
- циклы с ограничениями;
- agent/workflow;
- несколько специализированных исполнителей.

Не нужно начинать с большой multi-agent системы. Сначала соберите простой управляемый workflow из 2–3 шагов.

Официальная документация: https://docs.langchain.com/oss/python/learn

## Практическое задание

Соберите маленькую программу, в которой есть обычный алгоритм и AI как один из его компонентов.

Минимум:

1. Функция `ask_model(...)` вызывает модель и возвращает проверяемый результат.
2. Программа умеет работать минимум с двумя моделями или провайдерами через общий интерфейс. Если второго API-доступа нет, сделайте второй адаптер как mock и явно пометьте, что живой вызов не проверен.
3. Есть функция `route_task(...)`, которая по понятному правилу выбирает модель или обработчик.
4. Есть хотя бы один настоящий local tool, например `calculate_total(...)` или `get_local_record(...)`.
5. Аргументы tool проверяются до выполнения.
6. Ошибка модели не должна ломать всю программу: предусмотрите timeout/error/fallback.
7. В логе видно: какой шаг выполнялся, какая модель использовалась и какой tool был вызван.
8. API-ключи не попадают в репозиторий.

### Пример алгоритма

```text
входная задача
    ↓
route_task()
    ├─→ модель A
    ├─→ модель B
    └─→ обычная функция без AI
             ↓
        tool/function
             ↓
       проверка результата
             ↓
          ответ
```

## Когда считать пункт освоенным

Вы должны суметь своими словами объяснить:

- чем обычный API-вызов модели отличается от tool calling;
- зачем нужен единый слой для нескольких моделей;
- что делает orchestration framework;
- где решение принимает обычный код, а где — модель;
- как заменить одну модель другой, не переписывая весь алгоритм;
- почему любые действия модели нужно ограничивать и проверять.

И показать работающий небольшой пример.
