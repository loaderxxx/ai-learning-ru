# 4. Сравниваем пользу и стоимость координации

**Цель:** решить, оправдано ли разделение именно вашей задачи. Ориентир — 60–120 минут. Выигрыш на двух примерах не переносится автоматически на другие задачи.

## Подготовьте сопоставимые записи

Для каждого случая нужны обе стратегии: `solo` и `roles`. Используйте одинаковый исходник и критерий. По возможности чередуйте порядок выполнения на разных случаях: сначала solo, затем roles; на следующем — наоборот. Проверяющему можно скрыть способ получения карточки. Это уменьшает некоторые смещения, но не превращает маленький опыт в строгий научный результат.

`accepted` означает, что итог модели принят человеком **без исправления человеком**. Время `human_minutes` включает подготовку, проверку, ручную передачу и исправления, если они выполнялись. Для ролей суммируйте все этапы. Ожидание модели, число попыток и комментарии храните в отдельном [протоколе эксперимента](../templates/EXPERIMENT.md).

## Формат для программы

Создайте `my-runs.json` в своей рабочей папке. Минимальная пара записей:

```json
{
  "kind": "measured",
  "runs": [
    {"case_id":"C01","strategy":"solo","accepted":true,"human_minutes":4,"tokens":null},
    {"case_id":"C01","strategy":"roles","accepted":false,"human_minutes":7,"tokens":null}
  ]
}
```

**Числа выше — пример формы, не ваши измерения.** Замените все значения фактическими наблюдениями, добавьте остальные пары. `tokens: null` означает отсутствие достоверного счётчика. Если токены доступны, внесите общую сумму всех входов и выходов стратегии; разные способы учёта нужно объяснить. Для повторов используйте отдельный файл: дубликаты одной пары отклоняются.

Из корня репозитория:

```bash
python next/lab/compare_runs.py my-runs.json
```

Программа только проверяет записи и суммирует принятые случаи, минуты и токены. Она **не вызывает модели и не оценивает ответы**. Для ознакомления есть [синтетический пример](../fixtures/comparison-example.json) с `kind: illustrative_synthetic`. Его числа вымышлены и не являются доказательством превосходства ролей. При неизвестных токенах итог остаётся null.

## Примите решение

Посмотрите не только на принятые случаи, но и на ошибки каждого способа и время человека. Если результат одинаков, а передача добавляет работу, оставьте простую схему. Если роли находят важные ошибки, проверьте повторяемость на новых случаях и заранее определите допустимые затраты.

Для нового условия придумайте два случая, которых не было при настройке. Сохраните все неудачные попытки. В финале напишите: «Для этих условий выбираю …, потому что …; остаётся непроверенным …». Допустим итог «данных недостаточно».

Теперь у вас есть полный учебный кейс: проверка входа, работающий прототип, исследование локального запуска и обоснованный выбор организации работы. Фактически невыполненные шаги оставьте открытыми в своём отчёте.
