# 07. Review: требуйте воспроизводимые замечания

**Результат:** рецензия на изменение с проверенными замечаниями и решением о готовности. «Код выглядит чистым» не является проверкой требований.

## Дайте проверяющему независимую задачу

Автору удобно объяснять, почему решение должно работать. Проверяющий ищет, при каком допустимом условии оно нарушит контракт. Если второй агент получил только уверенное описание автора, он может повторить тот же вывод. Для review нужны исходное требование, базовая версия, diff и команда проверки.

Проверять следует конкретный commit или точное рабочее состояние. Замечание к прошлой версии может быть уже исправлено, а успешный тест к ней не покрывает новый патч. Перед передачей выполните:

```bash
git status --short
git diff --stat
git diff
```

Эти команды показывают незакоммиченные изменения. Для review ветки дополнительно выберите корректную базу сравнения; не считайте, что отсутствие рабочего diff означает отсутствие изменений в ветке.

## Формат полезного замечания

Каждое замечание содержит место, нарушенное условие, вход для воспроизведения, наблюдаемый эффект и серьёзность. Пример: «Вариант принимает логический приоритет; вызов с `True` проходит вместо ValueError; это нарушает тип поля». Это проверяемо. Фраза «улучшить валидацию» слишком широка.

Серьёзность связана с последствием. Потеря записи, обход прав или частичный пакет обычно важнее предпочтения по имени переменной. Не смешивайте обязательное исправление и редакционное пожелание в один список без приоритета.

## Практика на двух ошибках

Попросите ИИ проверить `OverwritesConflict` и `LeaksMutableSnapshot` по SPEC, не показывая названия тестов. Запишите предполагаемые проблемы. Затем воспроизведите их контрактным набором либо своим минимальным сценарием. Если замечание не воспроизводится, уточните условие или пометьте его неподтверждённым.

Теперь дайте эталон. Модель может продолжить искать похожий дефект и выдать ложное срабатывание. Попросите назвать точный путь изменения внутреннего состояния. Если наружу возвращается глубокая копия, прежнее замечание о ссылке требует нового доказательства.

## Учитывайте то, чего diff не показывает

Изменение может быть локально разумным и нарушить внешний договор: тип ответа, порядок элементов, обработку повторов, совместимость старого файла данных. Поэтому review читает требования и вызывающий код вокруг изменения, а не только изменённые строки.

Проверьте также изменение тестов. Удалённый assertion или превращённая в warning ошибка может объяснить внезапный зелёный результат. Это не обязательно злоупотребление: тест мог устареть. Но причина должна следовать из нового согласованного требования.

## Решение после review

Используйте [шаблон REVIEW](../templates/REVIEW.md): подтверждённые дефекты, неподтверждённые гипотезы, выполненные команды и оставшиеся риски. После исправления повторите относящиеся к замечанию проверки и интеграционный набор. Второй агент не гарантирует независимость ошибок; окончательное решение опирается на данные.

**Готово:** есть хотя бы один проверенный контрпример или явное заключение «на проверенных сценариях нарушения не обнаружены». Не пишите «ошибок нет» по ограниченному просмотру.
