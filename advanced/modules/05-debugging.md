# 05. Отладка: проверяйте гипотезу до новой генерации

**Результат:** воспроизводимый дефект, объяснённая причина и небольшой патч, который закрывает именно её.

## Симптом не указывает причину

«После неудачного пакета появилась запись» можно объяснить несколькими механизмами: запись выполняется слишком рано, обработчик ошибки повторяет операцию, чтение показывает старый кеш или тест использует общий объект. Попросить «исправь атомарность» без воспроизведения — значит позволить агенту выбрать любую историю.

Для эксперимента используйте заранее дефектный вариант:

```bash
python3 advanced/labs/change-gym/run_checks.py --variant partial_batch --suite contract
```

Найдите конкретное падение. В `PartialBatchWrite.submit_batch` успешные элементы уже меняют `self`, когда следующий элемент вызывает ошибку. Это подтверждается наблюдением списка после исключения. Здесь нет базы данных и конкурирующих процессов; не объясняйте локальную ошибку «гонкой сервера».

## Минимальная запись об ошибке

1. Начальное состояние: одна существующая запись `old`.
2. Действие: пакет из допустимой `new` и записи с приоритетом 4.
3. Ожидание: `ValueError`; состояние только `old`.
4. Наблюдение: исключение есть, но `new` остаётся.
5. Среда и вариант: Python, commit, `partial_batch`.

Для каждой гипотезы задайте различающий эксперимент. Если «общий объект тестов», создайте новый store. Если «порядок обработки», переставьте ошибочную запись на первое место. Сравнение поможет локализовать момент изменения состояния.

## Не лечите исключение его подавлением

Патч `except ValueError: return []` меняет сообщение об успехе, но не отменяет уже выполненную запись. Патч «удалить последнюю запись» может удалить не ту запись или потерять прежнее состояние. Корректное решение должно соответствовать модели данных: в учебном примере можно сначала применить весь пакет к отдельному состоянию, затем заменить исходное при успехе. Для настоящей базы нужен её транзакционный механизм и проверки отказа.

## Работа с ИИ

Дайте модели короткий отчёт, SPEC и функцию. Попросите три вещи: предполагаемую причину с указанием кода, эксперимент, который её отличает от альтернативы, минимальную правку. Если модель не видела окружение, её объяснение остаётся гипотезой до запуска.

Ограничьте число итераций без нового наблюдения. Если третий патч снова не объясняет падение, вернитесь к минимальному сценарию. Повторная генерация с тем же ошибочным предположением редко даёт новую информацию.

## Проверка исправления

Сохраните тест, который падал до правки и проходит после. Добавьте связанный случай: конфликт внутри пакета после нескольких допустимых элементов. Сравните состояние целиком, включая старые записи; проверки только длины недостаточно. После этого запустите прежние контрактные тесты, чтобы не потерять идемпотентность.

**Готово:** в отчёте есть переход «наблюдение → причина → изменение → повторный запуск». Дополнительно проверьте, что убранные временные логи не содержали данные, которые нельзя публиковать. Наши данные синтетические, но привычка переносится на реальные проекты.

Источник о проверяемой отладке: [Claude Code best practices](https://code.claude.com/docs/en/best-practices). Учебный дефект и его сценарий разработаны для этого репозитория.
