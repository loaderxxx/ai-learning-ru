# 04. Спецификация, которая помогает принять изменение

**Результат:** одна небольшая функция описана так, что два человека независимо создают совместимые реализацию и проверки.

## Зафиксируйте наблюдаемое поведение

Задача «добавить удобный фильтр» допускает слишком много трактовок. Для тренажёра выберем `list_jobs(min_priority=None)`: без аргумента работает как раньше; с целым числом 0–3 возвращает записи с приоритетом не ниже порога. Boolean, float, строка и число вне диапазона дают `ValueError`. Порядок по ID и независимость снимка сохраняются.

Новые требования дополняют старые. Они не разрешают менять повторы ID, правила пакета или валидацию заголовка. Именно это часто теряется, когда агент видит новую просьбу, но не видит существующий контракт.

## Таблица примеров

| Начальные приоритеты | Параметр | Ожидаемое поведение |
|---|---|---|
| 0, 1, 3 | Не передан | Все записи, прежний порядок |
| 0, 1, 3 | 1 | Записи с 1 и 3 |
| 0, 1, 3 | 3 | Только запись с 3 |
| Пусто | 2 | Пустой список |
| Любые | `True` | Ошибка аргумента |
| Любые | `4` | Ошибка аргумента |

Добавьте случай изменения возвращённого словаря: внутреннее состояние должно остаться прежним. Таблица задаёт внешнее поведение; она не диктует, какой цикл или comprehension написать.

## Нарежьте работу по результатам

Первый шаг — уточнить подпись функции и совместимость. Второй — проверки нового поведения и старого вызова без аргумента. Третий — реализация. Четвёртый — общий запуск и просмотр diff. Каждый шаг даёт наблюдаемый результат. «Проработать архитектуру», «добавить интеллект» или «сделать профессионально» без критерия не помогают остановиться.

Если агент предлагает переписать хранение на базу данных ради этого фильтра, попросите показать требование, которое этого требует. Иногда изменение архитектуры оправдано; в данной задаче такой зависимости нет. Размер плана должен соответствовать масштабу правки.

## Запрос к агенту

```text
Добавь фильтр min_priority по приложенной спецификации.
Сначала назови затронутый интерфейс и два риска совместимости.
Сохрани остальные инварианты SPEC. Покажи проверки старого и нового вызова.
Если для реализации требуется изменить несвязанное поведение,
объясни зависимость до такой правки.
```

Проверьте план по коду: существует ли названный файл, действительно ли эта функция обслуживает нужный путь, не забыт ли другой вызывающий код. Текст, уверенно называющий несуществующую функцию, не становится планом после форматирования в список.

## Когда требования меняются

Представьте уточнение: порог теперь исключительный, `priority > min_priority`. Это новая семантика. Отметьте изменённый пример, обновите версию спецификации и тест. Не оставляйте одновременно два равноправных описания `>=` и `>` в разных файлах. В записи о решении объясните, почему прежнее поведение заменено.

**Готово:** проверяющий способен написать тест до просмотра вашей реализации; старый вызов сохраняет результат; изменение не затрагивает несвязанные инварианты. Пройдите [шаблон изменения](../templates/CHANGE.md), затем переходите к отладке или проверке тестов.
