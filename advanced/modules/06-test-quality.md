# 06. Проверяйте тесты, которые написал ИИ

**Результат:** набор, который обнаруживает выбранное нарушение требования, и объяснение, чего он пока не доказывает.

## Почему зелёный результат бывает слабым

Smoke-тест подтверждает, что программа вообще запускается на простом примере. Он не обязан проверять повторный запрос, конфликт, границу диапазона и восстановление после ошибки. Если агент написал реализацию и тесты по одному неверному предположению, они могут согласованно ошибаться.

Наш `compare_suites.py` запускает одинаковые наборы на эталоне и шести заранее написанных дефектных классах. Скрипт не меняет ваши исходные файлы и не вызывает модель. Это ограниченная демонстрация mutation testing, а не универсальный движок автоматического изменения программы.

| Дефект | Почему простая проверка его пропускает | Нужный контрпример |
|---|---|---|
| Пустой заголовок принят | Проверяется только непустой | Строка из пробелов |
| `True` принят как приоритет | `isinstance(True, int)` истинно | Boolean отдельно от 0/1 |
| Повтор создаёт дубликат | ID в тестах всегда разные | Один запрос дважды |
| Конфликт перезаписывает запись | Нет второго содержимого | Тот же ID, другой title |
| Пакет частично записан | Все элементы допустимы | Ошибка после успешного элемента |
| Снимок меняет реестр | Результат только читается | Изменение возвращённого словаря |

## Независимый ожидаемый результат

Не вычисляйте ожидаемый ответ тем же методом, который тестируете. Проверка `result == implementation(input)` не создаёт независимого основания. Исходите из примера требования: после неудачного пакета должно остаться ровно прежнее состояние.

Иногда лучше свойство, а не один ответ. Например, повтор одного допустимого запроса не меняет число записей; изменение снимка не меняет последующее чтение; порядок независимых уникальных вставок не меняет отсортированный результат. Каждое свойство тоже имеет область применимости: конфликтующие записи не являются независимыми.

## Практика

Возьмите один дефект и сначала напишите свой тест без просмотра готового `ContractChecks`. Запустите его на эталоне и дефектном варианте. Эталон должен пройти, дефект — не пройти. Если падают оба, возможно, тест требует поведения, которого нет в SPEC. Если проходят оба, контрпример недостаточен.

Затем придумайте седьмой вариант ошибки. Например, неправильная верхняя граница длины ID. Сначала опишите, какое требование он нарушает. Добавьте проверку ровно на границе и по обе стороны. Не подстраивайте ожидаемый результат под текущую функцию.

## Как читать показатели

В демонстрации 6/6 означает только обнаружение шести известных ошибок. Это не 100% качество кода и не независимая оценка модели. В настоящем mutation testing некоторые изменения эквивалентны исходному поведению, другие не соответствуют вашему домену. Разбирайте оставшиеся варианты, вместо того чтобы любой ценой добиваться общего процента.

Покрытие строк полезно как подсказка, куда не заходили тесты. Оно не устанавливает, что проверено правильное условие. Разные варианты проверки смотрят на разные свойства продукта.

**Готово:** один новый тест выявляет конкретный дефект и не отвергает эталон. В отчёте записано, какие требования остаются без проверок. Источники: [Stryker — mutation testing](https://stryker-mutator.io/docs/) и [Python unittest](https://docs.python.org/3/library/unittest.html).
