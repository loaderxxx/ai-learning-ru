# 01. Контекст: найдите нужное и проверьте актуальность

**Результат:** небольшая карта кода и комплект файлов для одной задачи. Нужна не вся история проекта, а достаточное основание для конкретного изменения.

## Четыре разных вида сведений

| Вид | Пример в лаборатории | Как использовать |
|---|---|---|
| Действующее требование | SPEC.md | Определяет ожидаемое поведение |
| Текущее поведение | job_store.py | Показывает, что реально делает программа |
| Наблюдение | Ошибка теста | Подтверждает конкретное расхождение |
| Историческое обсуждение | legacy-note.md | Объясняет прошлое; требует проверки статуса |

Сгенерированное резюме — пятый, производный вид. Оно помогает ориентироваться, но может пропустить условие. Если резюме и файл расходятся, сравните версии и первичный документ. Не соединяйте их догадкой.

## Поиск по символу и исследование потока

Когда известна ошибка или функция, начните с точного поиска. Для нашей задачи:

```bash
rg -n 'submit_batch|ConflictError|priority' advanced/labs/change-gym
```

Затем проследите путь: вход → нормализация → проверка повторного ID → изменение состояния → выдача результата. Найдите тест каждого перехода. Не просите агента просто «понять весь репозиторий» без вопроса, ответ на который нужен сейчас.

В текущей [документации Cursor Search](https://cursor.com/docs/agent/tools/search) описан Instant Grep. Старые статьи об обязательных embeddings и прежнем индексировании не следует автоматически переносить на установленную версию. Поиск кандидатов и включение текста файла в запрос модели — разные действия. Успешный поиск ещё не означает, что агент прочитал найденное условие.

## Эксперимент с устаревшей заметкой

Сформулируйте задачу: «Как должен вести себя повторный ID с другим заголовком?». Дайте модели архивную заметку вместе с SPEC. Не скрывайте маркировку архива. Попросите назвать действующее правило и его источник.

Плохой ответ предлагает перезапись, потому что встретил её в истории. Приемлемый ответ замечает отменённое решение и проверяет конфликт. Правильное объяснение без последующего теста ещё не подтверждает правильный код.

Усложнение: добавьте новую версию спецификации, которая меняет только диапазон приоритета. Запишите дату/версию и явно укажите заменяемый пункт. Проверьте, не изменил ли агент заодно правила ID или атомарность. Это упражнение на точность изменения контекста, а не конкурс длинных промптов.

## Соберите контекст для правки

В [шаблон контекста](../templates/CONTEXT.md) внесите:

1. Одно требуемое изменение и начальный commit.
2. Действующую спецификацию и функцию, которую оно затрагивает.
3. Один существующий пример правильного поведения.
4. Сценарий ошибки с фактическим выводом.
5. Ограничение: какие интерфейсы должны остаться совместимыми.

Сначала позвольте агенту запросить недостающий файл. Не добавляйте все логи и всю переписку «на всякий случай». Если рабочее дерево изменилось после составления пакета, обновите привязку к версии. Иначе модель будет рассуждать о коде, которого уже нет.

## Как оценить результат

Другой разработчик по карте должен найти нужную функцию, актуальное правило и проверку за несколько понятных переходов. Число файлов само по себе не является метрикой качества: маленький пакет тоже бывает неполным.

**Готово:** агент ссылается на актуальное требование, объясняет отменённое решение и предлагает изменение в нужной части кода. Для проверки переноса повторите задачу с другим полем, сохранив остальные условия.

Дополнительное чтение: [контекст для агентов, Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). Описанный здесь эксперимент — наше собственное упражнение.
