# 13. Интерфейс: проверьте пользовательский путь

**Результат:** для вашего UI есть набор сценариев и фактические доказательства прохождения. Этот модуль — расширение: в поставляемом тренажёре веб-интерфейс не реализован.

## От картинки к действию

Скриншот показывает одну страницу в одном состоянии. Он не подтверждает, что кнопка создаёт запись, двойное нажатие не даёт дубликат, ошибка сохраняет введённый текст, а клавиатурой можно пройти форму. Красивый mockup полезен для обсуждения, но проверка поведения нужна отдельно.

Если вы добавили к реестру форму, опишите минимальный путь: ввести ID, заголовок и приоритет → отправить → увидеть запись. Затем добавьте отказ: повторить ID с другим заголовком → увидеть понятное сообщение → убедиться, что старая запись не изменилась.

## Матрица состояний

| Состояние | Что видит пользователь | Что проверяем в данных |
|---|---|---|
| Пустой реестр | Понятный способ начать | Записей действительно нет |
| Запрос выполняется | Объяснимое ожидание | Повторный клик не создаёт новую операцию |
| Успех | Новая запись и понятный результат | Содержимое совпадает с нормализованным входом |
| Ошибка валидации | Конкретное поле и причина | Записи не добавились |
| Конфликт ID | Объяснение конфликта | Старая запись сохранена |
| Недоступный сервис | Возможность повторить позже | Не показан ложный успех |

Блокировка кнопки сама по себе не обеспечивает идемпотентность серверной операции. Двойной запрос может прийти от повторной попытки, другого клиента или после timeout. Поэтому договор на стороне сервиса сохраняется.

## Используйте доступные средства проверки

При наличии браузерного инструмента попросите агента выполнить конкретный сценарий и показать результат. Если такого инструмента нет, пройдите сценарий вручную. Не называйте сгенерированный скриншот снимком работающего приложения.

В автоматизации [Playwright](https://playwright.dev/docs/best-practices) рекомендует проверять пользовательское поведение и использовать устойчивые локаторы. На уровне собственного проекта это означает: искать кнопку по роли и доступному имени, а не случайному CSS-классу; проверять наблюдаемый результат, а не только успешный `click`.

Псевдосценарий: открыть форму → заполнить поля → нажать «Добавить» → проверить запись → отправить конфликтующий вариант → проверить сообщение и исходную запись. Это план теста, не готовый исполняемый Playwright-файл: конкретные локаторы зависят от вашего UI.

## Проверьте состояние после ошибки

Обновите страницу, повторите действие, измените порядок операций. Используйте отдельные синтетические данные на каждый тест, чтобы успешный прошлый запуск не маскировал нынешнюю ошибку. Если внешний сервис подменён fixture, отдельно обозначьте, что его настоящая интеграция не проверялась.

Проверьте клавиатурный фокус, подписи полей, читаемость ошибок и узкий экран. Автоматический аудит помогает обнаружить часть проблем доступности, но не доказывает полное соответствие всем требованиям.

**Готово:** сохранены версия приложения, условия запуска, выполненные шаги и фактические снимки/отчёт. Если UI ещё нет, можно подготовить матрицу, но практическое прохождение модуля остаётся открытым.
