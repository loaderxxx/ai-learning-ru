# 10. Параллельная работа: разделите задачи и проверьте соединение

**Результат:** два независимых изменения подготовлены в отдельных рабочих деревьях и проверены вместе. Выполнять их можно по очереди одному человеку; платные параллельные агенты не обязательны.

## Какие задачи действительно независимы

Добавление фильтра и написание пояснения к существующему контракту могут идти отдельно. Два изменения подписи одного метода зависят друг от друга. Разные файлы тоже не доказывают независимость: один меняет формат данных, другой читает его по старому правилу.

Перед разделением запишите общую базовую версию, границы каждой задачи, общий интерфейс и кто объединяет результаты. Это техническая договорённость для конкретного проекта. Число агентов само по себе не является целью.

## Две рабочие копии через Git

Команды ниже выполняются в вашей отдельной учебной Git-копии. Сначала убедитесь, что нужное исходное состояние закоммичено; незакоммиченные изменения основной папки автоматически не появляются в новых worktrees.

```bash
git status --short
git rev-parse --show-toplevel
git worktree add -b practice/filter ../ai-practice-filter HEAD
git worktree add -b practice/docs ../ai-practice-docs HEAD
git worktree list
```

Имена веток и соседние папки должны быть свободны. Не используйте `--force` для обхода конфликта. В каждом каталоге работает своя ветка, при этом Git-объекты репозитория общие. Подробности — [git-worktree](https://git-scm.com/docs/git-worktree).

## Задания

Первый участник реализует согласованный фильтр и его тесты. Второй проверяет инструкцию запуска и дополняет объяснение ограничений. Каждый получает короткий [handoff](../templates/HANDOFF.md), одинаковую исходную спецификацию и свою область изменения. Не направляйте двух исполнителей одновременно писать в одну обычную папку.

Перед объединением каждый фиксирует проверенный результат отдельным commit. Просмотрите список и содержимое этих commits, затем примените их в интеграционной ветке обычным merge или cherry-pick. Здесь намеренно нет команды с выдуманным SHA: используйте фактические commits своих задач.

## Проверка после объединения

Отсутствие текстового merge conflict не означает отсутствие смыслового конфликта. Запустите весь контрактный набор и новые сценарии. Проверьте, что документация описывает именно объединённое поведение. Если одна ветка поменяла параметр с включительной границы на исключительную, это надо согласовать явно.

Worktree изолирует файлы, но не обязательно порты, внешнюю базу, аккаунт и ресурсы машины. Два процесса могут столкнуться на одном порту или записать в один внешний каталог. Для расширенного проекта назначьте отдельные тестовые ресурсы.

## Когда параллелизм не нужен

Если задачу быстрее сделать одним небольшим diff, координация может стоить больше реализации. Сначала измеряйте время до принятого объединённого результата. Не считайте два одновременно открытых чата удвоением производительности.

[Codex Worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees) описывает интеграцию в продукте. Доступность интерфейса проверяйте в своей среде; обычные команды Git остаются отдельным вариантом.

**Готово:** у каждого изменения известна версия, объединение проверено, чужая работа сохранена. Удаляйте учебный worktree только после проверки статуса и сохранения нужных commits; не применяйте принудительное удаление ради порядка.
